# 关键信息基础设施安全保护条例

> 国务院令第745号，2021年9月1日起施行。

这部条例不是另起一套与等保平行的体系，而是在网络安全等级保护基础上，对被认定为关键信息基础设施的运营者提出更高强度、更明确责任和更强监管联动的重点保护要求。

[法规概览](#overview) · [安全要求与实施](#requirements) · [法规原文](#reference)

## 法规概览 {#overview}

| 项目 | 内容 |
| --- | --- |
| 适用对象 | 被保护工作部门认定并通知的关键信息基础设施运营者 |
| 核心基础 | 网络安全等级保护制度 |
| 核心主线 | 认定与边界 → 三同步 → 专门机构 → 持续监测与年度评估 → 供应链 → 事件处置与报告 |
| 关键特点 | 主要负责人责任、专门安全管理机构、关键岗位背景审查、年度检测评估、关键采购和供应链控制 |

可以把关基保护压缩成一句话：**先把“哪些系统是关基、边界在哪里”搞清楚，再让组织、建设、监测、供应链、评估和事件响应围绕这张清单持续运行。**

下文按 **“法规要求 → 落实与验收”** 展开：每项要求同时说明实施动作与可验证的验收标准。关基认定以保护工作部门通知为准，企业不能仅凭内部判断自行宣布或取消关基身份。

## 安全要求与实施 {#requirements}

| 核心主题 | 达成状态 |
| --- | --- |
| 关基范围与边界 | 哪些系统属于关基、关键资产和依赖关系清楚 |
| 组织责任 | 主要负责人、专门安全机构和关键岗位真正履职 |
| 三同步 | 新建改扩建时安全和业务一起规划、建设、验收 |
| 持续监测与评估 | 关键系统持续可见，年度检测评估真实发现问题 |
| 供应链与采购 | 关键产品、服务、外包和云依赖风险受控 |
| 应急与报告 | 重大事件和威胁能够快速处置、恢复和报告 |

### 明确认定结果、边界和关键依赖

**法规要求｜第8—11条。** 保护工作部门负责组织认定关键信息基础设施并通知运营者；关基发生较大变化、可能影响认定结果时，应及时报告。

**落实与验收。**

- 维护正式关基认定结果和内部关基清单，记录对应保护工作部门及联系人。
- 对每个关基明确业务范围、网络边界、关键资产、关键数据、外部依赖和上下游关系。
- 架构、业务、组织、合并分立、关键供应链等重大变化进入关基影响判断流程。
- 认定变化、范围变化和保护责任变化形成正式记录并同步到资产、应急和评估体系。

**验收标准。**

- 随机抽一项认定关基，能否现场拿出认定通知、边界图、关键资产和关键依赖？
- 从实际生产资产反查关基清单，是否存在关键系统已迁移或新增但清单未更新？
- 最近一次重大架构或业务变化是否触发过关基影响判断？
- 关基边界与等保定级对象、CMDB和监测范围是否一致？

### 落实安全与关基“三同步”

**法规要求｜第12条。** 安全保护措施应当与关键信息基础设施同步规划、同步建设、同步使用。

**落实与验收。**

- 在立项阶段明确安全目标、预算、等保/关基要求、关键控制和验收标准。
- 架构评审、研发、采购、上线和变更流程内置关基安全门禁。
- 新建、改建、扩建项目在正式投产前完成安全验证，未达到关键基线不得以“后补整改”替代。
- 安全能力建设和业务容量、架构演进同步规划，避免上线后再临时拼接监控和防护。

**验收标准。**

- 随机抽一个近一年关基改造项目，安全预算和需求是在立项时出现还是上线前才补？
- 从需求、架构、采购、测试、上线记录能否看到安全要求连续存在？
- 找一个曾经带风险上线的项目，为什么门禁没有阻断？
- 新系统投产当天，日志、监测、告警、备份和应急是否已经可用？

### 压实主要负责人和专门安全管理机构责任

**法规要求｜第13—16条。** 运营者主要负责人对关基安全保护负总责，应设置专门安全管理机构并保障其履职，相关负责人和关键岗位人员按要求开展安全背景审查。

**落实与验收。**

- 明确主要负责人对关基重大风险、年度计划、重大投入和重大事件的决策责任。
- 设置真实运行的专门安全管理机构，保障人员、经费和参与重大信息化决策的权利。
- 明确安全机构、业务、技术、运维、采购和供应商的责任矩阵。
- 对专门安全机构负责人和关键岗位按要求开展背景审查并保留记录。

**验收标准。**

- 最近一次重大关基风险是否进入主要负责人决策，留下了什么具体决策？
- 专门安全管理机构是否能阻断高风险上线，还是只有咨询权？
- 机构人员、预算和职责是否与实际关基规模匹配？
- 随机抽一个关键岗位，背景审查是否在上岗前完成，岗位变化后是否需要复核？

### 建立持续监测和风险发现能力

**法规要求｜第15条等。** 运营者应建立网络安全监测预警、风险管理和技术防护机制，持续提升关基保护能力。

**落实与验收。**

- 关基关键主机、网络、身份、应用、数据和外部暴露面进入持续监测。
- SIEM、NDR/EDR、漏洞、威胁情报、配置基线和业务异常形成统一风险发现链路。
- 监测范围与关基资产清单动态联动，新增资产不能长期处于监控盲区。
- 重大风险进入统一事件和整改流程，有Owner、时限、复测和管理层升级机制。

**验收标准。**

- 从关基资产清单随机抽资产，是否都有日志、终端/主机或网络监测覆盖？
- 从监测平台反查过去30天新增资产，是否全部进入关基清单和监控？
- 随机抽一条高危告警，最终处置结论基于什么证据？
- 长期未关闭的风险为什么没有升级？

### 每年至少开展一次检测和风险评估

**法规要求｜第17条。** 运营者应自行或者委托网络安全服务机构，对关基每年至少进行一次网络安全检测和风险评估，并按要求报送情况。

**落实与验收。**

- 每年覆盖资产、架构、配置、漏洞、账号权限、边界、供应链、应急和关键业务连续性等核心风险。
- 检测评估不仅审制度，还要结合技术检测、配置核验、真实数据和抽样验证。
- 问题形成整改任务，明确责任人、期限、风险接受条件和复测结果。
- 重大变化、重大事件或高风险暴露时触发专项评估，不等下一年度周期。

**验收标准。**

- 最近一次年度评估实际发现了哪些技术或管理问题？
- 如果连续多年问题数量极少，评估是否真正深入到配置和真实运行？
- 随机抽一个评估问题，能否从发现一直追到整改和复测证据？
- 年度评估是否覆盖当年新增的重要系统和重大架构变化？

### 管理关键产品、服务和供应链风险

**法规要求｜第19、20条等。** 运营者采购网络产品和服务，应按要求关注安全可信和供应链风险；可能影响国家安全的，依法申报网络安全审查；与提供者签订安全保密协议等。

**落实与验收。**

- 建立关基关键产品、服务、云、外包、软件供应链和高权限供应商清单。
- 采购前开展安全尽调和风险评估，合同明确安全、保密、漏洞、事件通知、人员、远程访问和退出要求。
- 对可能触发网络安全审查的采购建立前置判断和法务合规升级机制。
- 供应商高权限访问实施专用账号、最小权限、时间窗口、审批、监控和回收。
- 合作终止时验证账号、凭证、数据、副本和远程通道全部退出。

**验收标准。**

- 从VPN、PAM、云IAM和运维通道反查供应商，是否有未进入供应商清单的第三方？
- 随机抽一项关键采购，安全评估是否在合同签订前影响了方案？
- 供应商工程师离场后，账号和长期凭证是否仍有效？
- 谁负责判断某项采购是否可能触发网络安全审查，判断依据是否留痕？

### 建立专项应急、演练和恢复能力

**法规要求｜第15、18、25条等。** 运营者应制定关基网络安全事件应急预案，定期演练，重大事件和重大威胁按规定报告并采取处置措施。

**落实与验收。**

- 关基专项预案覆盖攻击、勒索、系统中断、数据泄露、供应链事件、关键依赖故障等场景。
- 明确指挥、技术处置、业务降级、取证、恢复、对外沟通和监管报告职责。
- 演练必须覆盖真实依赖和失败条件，如主负责人不可达、主链路中断、备用系统不可用。
- 关键业务定义恢复目标和恢复路径，并通过演练验证，而不是只写RTO/RPO数字。

**验收标准。**

- 最近一次演练是否真的切换或验证关键系统，而不只是桌面讨论？
- 给出“主机房不可用+关键供应商不可达”的场景，现场能否找到备用决策和恢复路径？
- 预案联系人中随机拨测一名，是否仍有效？
- 演练暴露的问题是否改变了系统、流程或资源配置？

### 及时报告重大事件、重大威胁和重要变化

**法规要求｜第11、18条等。** 关基发生较大变化可能影响认定结果的，应及时报告；发生重大网络安全事件或者发现重大网络安全威胁时，应按规定报告。

**落实与验收。**

- 建立事件、威胁和重大变化三类报告触发条件，明确保护工作部门、公安机关等报告对象和联系人。
- 与企业统一事件响应机制联动，避免关基事件只在技术团队内部关闭。
- 预置报告模板、决策路径、备用渠道和最小初报信息。
- 同一事件触发网络安全、数据安全、个人信息和行业监管义务时并行跟踪。

**验收标准。**

- 随机抽一件关基高危事件，是否进入过报告适用性判断？
- 给出“重大威胁已确认但尚未形成实际损失”的场景，团队是否知道是否需要报告？
- 主监管联系人不可达时，备用联系人和渠道是否可用？
- 重大架构变更是否存在“技术团队认为只是内部改造，因此未评估关基认定影响”的情况？

### 管住关基测试和外部探测活动

**法规要求｜第31条。** 未经授权不得对关基实施漏洞探测、渗透性测试等可能影响其安全的活动。

**落实与验收。**

- 红队、渗透测试、漏洞扫描、供应商测试和演练必须有明确授权、范围、时间窗口和应急联系人。
- 测试方案评估对生产稳定性、数据和关键依赖的影响，必要时设置限速、白名单和停止条件。
- 外部未授权扫描、探测和攻击行为进入监测、阻断和事件响应。

**验收标准。**

- 随机抽一次红队或渗透测试，能否拿出明确授权和生产风险控制措施？
- 第三方安全服务商是否可能凭长期账号自行扩大测试范围？
- 测试触发生产告警后，SOC能否区分已授权活动和真实攻击？
- 未授权探测出现时是否有明确升级和阻断流程？
