# 互联网信息服务管理办法

本文依据2024年12月6日第二次修订、2025年1月20日起施行的现行《互联网信息服务管理办法》整理，从互联网信息服务提供者的实际运营视角，把许可备案、专项前置审批、服务范围、内容安全、记录留存和监管协查转成可执行控制。

[法规概览](#overview) · [安全要求与实施](#requirements) · [法规原文](#reference)

## 法规概览 {#overview}

| 项目 | 内容 |
| --- | --- |
| 法规 | 《互联网信息服务管理办法》（2000年公布，2011年第一次修订，2024年第二次修订） |
| 现行版本施行 | 2025年1月20日 |
| 主要适用对象 | 在中国境内从事互联网信息服务的提供者 |
| 基本分类 | 经营性互联网信息服务实行许可；非经营性互联网信息服务实行备案 |
| 核心问题 | 许可/备案、专项前置审批、服务范围、编号公示、内容安全、记录留存、监管协查 |
| 关键硬约束 | 不得无证/无备案或超范围提供服务；相关记录按规定保存60日；发现明显违法信息应停止传输、保存记录并报告 |
| 官方来源 | [商务部法规库（来源：中国政府网）](https://policy.mofcom.gov.cn/claw/clawContent.shtml?id=102438) |

下文按 **“法规要求 → 落实与验收”** 展开：每项要求同时说明实施动作与可验证证据。新闻、出版、教育等专项业务以及 App、算法、深度合成、生成式 AI 等能力，还应叠加相应专项规则。医疗、药品等业务是否需要其他许可，应依据其各自现行专项法规判断，不能再把它们写成本办法第5条的列举事项。

## 安全要求与实施 {#requirements}

| 核心主题 | 达成状态 |
| --- | --- |
| 许可备案 | 每个线上服务都能对应有效许可、备案或专项审批 |
| 业务变更 | 新域名、新业务、商业模式变化先判断是否需要变更手续 |
| 内容治理 | 违法信息能够发现、停止传播、留证和报告 |
| 日志留存 | 法定记录真实产生、可查询且满足最低期限 |
| 监管协查 | 监管查询时能快速定位并提供真实记录 |

### 先确定经营性、非经营性和专项服务身份

**法规要求｜第3—8条。** 经营性互联网信息服务实行许可制度，非经营性互联网信息服务实行备案制度；从事新闻、出版、教育等依法需要主管部门审核同意的互联网信息服务，应在申请经营许可或者履行备案手续前取得相应同意。

**落实与验收。**

- 建立互联网服务清单，至少关联业务主体、域名/App、服务内容、收费模式、用户对象、ICP许可/备案和专项资质。
- 新业务上线前判断属于经营性还是非经营性，并判断是否触发增值电信业务许可或其他专项前置审批。
- 医疗、药品、金融等业务的专项资质单独依据对应现行规则判断，不把历史版本第5条的旧列举当作现行依据。
- 集团多主体、多域名场景明确哪个主体实际提供服务，不能用集团内另一主体的许可或备案笼统覆盖。
- 定期将线上资产发现结果与许可备案清单比对，发现未知域名、临时活动站和历史系统及时处置。

**验收证据。**

- 从公网实际发现的域名、App和小程序随机抽样，逐一找到对应运营主体和许可/备案依据。
- 从财务收费项目反查互联网服务，是否存在已经收费但仍按“非经营性服务”管理的业务？
- 给出“新增新闻资讯/在线医疗”等场景，团队能否区分本办法第5条义务与其他专项法规义务？
- 随机抽一个集团关联公司运营的站点，证照主体与实际合同、收款和用户协议主体是否一致？

### 保证实际服务不超出许可备案范围

**法规要求｜第11—12条。** 互联网信息服务提供者应按照经许可或备案的项目提供服务，不得超范围；变更服务项目、网站网址等事项应提前30日办理变更手续，并在网站主页显著位置标明许可或备案编号。

**落实与验收。**

- 产品立项、域名申请、商业化和重大功能变更流程关联许可备案检查。
- 服务项目、域名、主体等发生变化时，建立变更任务并跟踪到手续完成。
- 网站/App公示信息从统一证照数据源生成或定期校验，避免编号过期、主体不一致。
- 对已下线业务及时完成注销或变更，减少“备案有、业务无”与“业务有、备案无”的双向偏差。

**验收证据。**

- 比对当前线上首页/关于页面公示编号与监管备案信息，主体、域名和编号是否一致？
- 从最近一年重大产品变更中抽样，是否在上线前完成许可范围判断和必要变更？
- 从许可/备案清单反查线上服务，是否存在证照覆盖的业务已经完全变化却从未更新？

### 建立违法信息发现、停止传播和报告闭环

**法规要求｜第13、15—16条。** 提供者应保证信息内容合法；发现网站传输的信息明显属于禁止内容时，应立即停止传输、保存有关记录并向国家有关机关报告。

**落实与验收。**

- 将法规禁止内容转成内容分类、审核规则、模型/关键词策略和人工处置标准。
- UGC、评论、直播、搜索、推荐等不同传播入口都进入内容治理范围。
- 对明确违法信息形成“发现 → 停止传播/删除 → 保存记录 → 账号处置 → 报告判断”的事件链路。
- 内容处置记录保留原始内容、发现方式、传播范围、处置时间、操作人和报告情况，不能删除内容后失去审计事实。

**验收证据。**

- 从近期真实违法内容样本抽取一条，完整还原从首次发现到停止传播用了多久。
- 从评论、搜索结果、私信等边缘入口反查，是否存在主信息流管得严但其他入口漏控？
- 删除内容后还能否调取原始证据、传播范围和处置记录？
- 对达到报告条件的历史样本，是否能证明向正确机关完成了报告？

### 让法定记录真实产生并至少保存规定期限

**法规要求｜第14条。** 新闻、出版及电子公告等服务提供者应记录提供的信息内容及发布时间、互联网地址或域名；互联网接入服务提供者应记录用户上网时间、账号、互联网地址或域名、主叫电话号码等信息；相关记录备份保存60日，并在国家有关机关依法查询时提供。

**落实与验收。**

- 先按自身服务身份确定必须记录的字段，不把通用应用日志直接等同于法定日志。
- 日志字段在真实业务链路自动生成，统一时间、账号和网络标识口径，并防止普通人员任意修改或删除。
- 保存策略明确不少于法定期限；存储迁移、日志降采样和成本优化不能破坏最低留存要求。
- 建立按账号、时间、内容或网络标识检索的协查能力。

**验收证据。**

- 随机指定60日前后的一条真实业务记录，现场查询法定字段是否仍然完整。
- 从业务请求反向追踪日志，是否因异步、代理、NAT等原因丢失关键网络标识？
- 检查日志平台实际生命周期配置，而不是只看制度写着“保存60日”。
- 模拟监管按用户+时间窗口查询，团队能否在合理时间内定位并导出准确记录？

### 管理监管协查和证据提供

**法规要求｜第14、18条等。** 互联网信息服务提供者应依法接受有关主管部门监督管理，并在依法查询时提供相关记录。

**落实与验收。**

- 建立监管请求接收、身份/权限核验、内部审批、数据提取、复核和交付流程。
- 明确安全、法务合规、业务和运维责任，紧急协查有备用联系人。
- 交付内容遵循请求范围，保存请求依据、实际提供内容、时间和经办记录。
- 定期演练从历史记录中快速恢复事实，避免检查时才发现日志字段、时区或账号映射无法解释。

**验收证据。**

- 随机抽一笔历史监管协查，从原始请求到最终交付能否完整还原？
- 请求范围只涉及一个账号时，是否会因为工具限制而批量导出无关用户数据？
- 夜间紧急协查时，如果主要负责人不可达，是否仍有合法、可控的执行路径？
