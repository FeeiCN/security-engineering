# 中国人民银行业务领域数据安全管理办法

> 中国人民银行令〔2025〕第3号，2025年6月30日起施行。

本文面向安全、数据和合规负责人，把3号令从“法规条文”转换为“可以建设、可以验收、可以接受检查”的数据安全工作要求。

[法规概览](#overview) · [安全要求与实施](#requirements) · [法规原文](#reference)

## 法规概览 {#overview}

| 项目 | 内容 |
| --- | --- |
| 核心对象 | 中国人民银行业务领域数据及其处理活动 |
| 主要主体 | 金融机构以及经中国人民银行批准设立或者认定的其他机构 |
| 核心主线 | 数据资源目录 → 分类分级 → 全生命周期控制 → 风险监测 → 评估审计 → 事件应急 |
| 最关键变化 | 不只要求“有制度”，而是要求数据处理活动持续受控，重要/核心数据、高敏数据采取更强保护 |

可以把3号令压缩为一句话：**先知道数据在哪里、是什么级别，再把权限、导出、加工、传输、提供、接口、日志、评估和应急全部纳入可持续控制。**

下文按 **“法规要求 → 落实与验收”** 展开：每项要求同时说明实施动作与可验证的验收标准。实施建议用于帮助落地，不替代法条本身；涉及其他主管部门规则的，应叠加适用。

## 安全要求与实施 {#requirements}

| 核心主题 | 达成状态 |
| --- | --- |
| 数据资源目录与分类分级 | 数据在哪里、属于什么业务、什么等级和敏感度都清楚 |
| 组织责任与制度 | 数据安全责任有人承担，高风险动作有制度和审批 |
| 权限与数据使用 | 谁能看、能导、能改、能批量处理都最小化且可追溯 |
| 数据传输与提供 | 数据离开原系统或机构时目的、范围、接收方和安全措施都受控 |
| 接口与日志 | 批量访问入口清楚，行为有鉴权、限流、监测和审计 |
| 风险评估与审计 | 控制效果被周期性验证，问题真正整改闭环 |
| 应急与报告 | 数据安全事件能被及时发现、分级、止损、报告和复盘 |

### 建立并持续维护数据资源目录

**法规要求｜第8、10条。** 数据处理者应建立业务数据资源目录并持续维护，按照要求开展重要数据识别、申报和动态管理。

**落实与验收。**

- 统一维护业务数据资源目录，关联业务、系统、数据表/对象、负责人、来源、用途、共享关系和保存位置。
- 目录不能只靠人工填表，应结合数据库、数据平台、对象存储、消息系统和接口清单进行自动发现与人工确认。
- 新系统、新数据源、新共享关系和重大变更进入目录更新流程。
- 至少按法规要求定期复核，重要数据识别结果与目录保持一致。

**验收标准。**

- 从生产数据库、对象存储和数据平台随机抽资产，能否在目录中找到？
- 从目录反查真实系统，字段、负责人、数据流向是否仍准确？
- 最近一个新系统上线后多久进入目录？谁负责触发更新？
- 目录里的重要数据与实际申报、保护范围是否一致？

### 同时做好重要性分级和敏感性分类

**法规要求｜第7—10条。** 数据处理者应建立分类分级制度，识别一般、重要、核心数据，并依据敏感程度实施差异化管理。

**落实与验收。**

- 把“重要性等级”和“敏感性分类”作为两个维度管理，不能只用一套标签替代。
- 结构化数据项原则上有可执行的敏感性标签；重要/核心数据能够关联到业务、系统和责任人。
- 重要数据识别有明确依据、评审和申报流程；重大变化后重新判断。
- 分类分级结果能够实际驱动权限、加密、脱敏、导出、传输、日志和审批策略。

**验收标准。**

- 随机抽一个数据项：它的敏感性、重要性等级分别是什么，依据是什么？
- 找一个高敏但非重要数据、一个重要但非高敏数据，控制是否真的不同？
- 分类分级调整后，系统策略是否自动或及时跟着变化？
- 是否存在“系统没有标签，因此默认按一般数据处理”的情况？

### 明确组织责任和高风险处理审批

**法规要求｜第11—13条。** 数据处理者应建立组织责任、制度规范、人员管理和培训机制；重要数据处理者应设置相应安全负责人和管理机构。

**落实与验收。**

- 明确数据安全负责人、管理机构、业务数据Owner、系统Owner和关键岗位责任。
- 建立覆盖收集、使用、加工、导出、提供、委托、删除等活动的制度和操作规程。
- 高风险数据处理活动进入线上审批，审批人、理由、范围、有效期和后续操作都可追踪。
- 每年组织与岗位匹配的数据安全培训并保留记录。

**验收标准。**

- 随机抽一笔高敏数据导出：谁申请、谁审批、为什么需要、实际导出的范围是否一致？
- 数据安全负责人是否真的参与重要数据、高风险共享和重大事件决策？
- 离职、转岗或职责变更后，相关审批权和高权限是否及时变化？
- 培训是否覆盖真正会接触数据的研发、运营、DBA、分析师和外包人员？

### 落实最小权限和特权账号控制

**法规要求｜第14、29条等。** 数据访问应实施身份鉴别、权限控制和可追溯管理，对高敏数据和高权限访问采取更严格保护。

**落实与验收。**

- 建立统一身份、RBAC/ABAC、PAM、离转调回收和周期复核机制。
- DBA、平台管理员、运维等特权账号实名、最小授权、操作留痕并尽量采用强认证。
- 高敏数据批量查询、导出、明文查看采用二次授权或增强认证。
- 共享账号、长期临时权限和超期权限持续治理。

**验收标准。**

- 从一个高敏数据库反查全部可访问账号，是否每个都能解释业务必要性？
- 随机抽一个离职/转岗人员，权限何时被回收？
- DBA是否可以绕过业务审批直接批量查看或导出高敏数据？
- 临时权限到期后是否自动失效，还是依赖人工记得回收？

### 管住高敏数据的存储、展示、导出和传输

**法规要求｜第16、17、20、32、33、35条等。** 对高敏数据的终端存储、明文展示、导出和非受控渠道传输实施更严格限制，并按要求采取加密等保护措施。

**落实与验收。**

- 高敏数据原则上集中存储，不落个人终端和移动介质；例外场景统一审批并设置有效期。
- 默认以查询、脱敏展示替代原始数据导出；非必要不明文展示。
- 对外传输和跨网络传输采用合适的加密与受控传输渠道。
- 邮件、IM、公共网盘、移动介质等高风险通道默认限制高敏数据传播。
- 结合DLP、水印、下载审批、文件交换平台等实现技术控制和追责。

**验收标准。**

- 从终端DLP和文件审计反查：最近是否有高敏数据落盘、通过IM或网盘传播？
- 随机找一个“业务确需导出”例外，审批范围、导出内容、保存时间和删除是否一致？
- 高敏数据页面是否可以通过截图、接口、前端调试或批量查询绕过脱敏？
- 数据传输的加密要求是否只写在制度里，还是能从配置和流量证明确实生效？

### 管理加工、模型训练和新数据产生

**法规要求｜第18、19、34条等。** 数据加工应与合法目的相符，对加工产生的新数据重新识别风险并采取相应保护措施。

**落实与验收。**

- 训练、画像、聚合、标签、分析等加工活动明确目的、数据范围、使用期限和访问主体。
- 使用高敏数据进行加工或训练时采取脱敏、最小化、隔离、审批等增强措施。
- 对加工形成的新数据重新评估敏感性和重要性，不能沿用旧标签直接判断。
- 训练集、特征库、中间结果和模型输出纳入数据资产与访问治理。

**验收标准。**

- 随机抽一个模型或分析任务：训练数据来自哪里，是否超出原始收集目的？
- 中间数据、特征和训练副本是否进入目录，还是长期游离在临时目录和个人空间？
- 聚合后的数据是否因为“看起来不再敏感”就失去访问控制？
- 训练任务结束后，临时数据和副本是否真的清理？

### 控制数据对外提供、委托和第三方使用

**法规要求｜第21、22、28条等。** 对数据提供、委托处理等活动建立安全管理和风险控制，重要数据等高风险场景按要求开展风险评估。

**落实与验收。**

- 建立接收方/受托方清单，明确给谁、给什么、为什么、保存多久、如何退出。
- 数据提供和委托前开展必要的准入评估和审批，合同明确用途、范围、安全措施、事件通知、再委托和退出要求。
- 重要数据、高敏数据和大规模数据提供进入增强评估。
- 合作终止后验证访问关闭、数据返还或删除。

**验收标准。**

- 从API、文件交换、供应商账号和合同反向生成第三方数据流清单，是否和台账一致？
- 抽一个供应商，实际可访问的数据是否超出合同和审批？
- 合作终止后，账号、接口和数据副本是否全部关闭或清理？
- 第三方发生安全事件时，是否有明确通知时限和响应联系人？

### 管住API和批量数据访问入口

**法规要求｜第36条等。** 数据接口应进行清单化、鉴权授权、安全测试、访问控制和异常监测。

**落实与验收。**

- 建立动态API清单，关联数据类型、调用方、认证方式、权限、限流、负责人和版本。
- 新建和重大变更接口投产前完成鉴权、授权、越权、批量访问和异常行为测试。
- 高风险数据接口禁止匿名访问，批量能力设置频控、配额和监测。
- 接口调用日志进入集中审计和异常检测。

**验收标准。**

- 从网关、服务注册和流量反查API清单，是否存在未登记接口？
- 随机抽一个高敏数据API，能否通过参数遍历、越权或批量分页绕过预期控制？
- 接口变更后是否重新做安全测试，还是沿用旧结论？
- 异常高频调用出现时，是否能在分钟级发现并定位调用方？

### 保证关键数据活动可追溯

**法规要求｜第30条。** 应按数据等级和具体要求保留数据处理活动相关日志，满足审计和事件调查需要。

**落实与验收。**

- 对关键访问、查询、导出、修改、删除、共享、接口调用和管理操作统一留痕。
- 日志包含足够的主体、对象、时间、来源、动作和结果信息，并实施防篡改、权限隔离和集中存储。
- 按法规要求落实不同数据等级的日志留存期限，不能以平台默认保留期替代。
- 日志能够与身份、审批、工单和事件记录关联。

**验收标准。**

- 随机抽一次高敏数据导出，能否从审批一直追到具体执行人、查询条件和导出结果？
- 任取一个历史日期，日志是否仍可检索且字段完整？
- DBA或日志平台管理员能否无痕删除审计日志？
- 不同系统时间、身份和日志格式是否能在事件中形成完整时间线？

### 持续开展风险监测、评估、审计和培训

**法规要求｜第39—45条等。** 数据处理者应持续监测数据安全风险；重要数据处理者按要求开展风险评估、应急演练和合规审计，不同主体适用相应周期要求。

**落实与验收。**

- 联动DLP、数据库审计、SIEM、终端、API、账号和外部泄露情报形成风险监测。
- 按法规要求开展年度风险评估、周期性合规审计和应急演练，并将问题转化为整改任务。
- 对监管通报、重大漏洞、重大架构变化和重大事件触发专项检查。
- 评估和审计不仅看制度，还要抽样验证真实运行数据和控制效果。

**验收标准。**

- 最近一次评估/审计发现了什么实质性问题？如果连续多年“零问题”，抽样方法是否有效？
- 风险监测发现异常后，是否真正进入事件、整改或例外流程？
- 演练是否覆盖负责人不可达、日志不完整、数据泄露范围暂不清楚等真实困难？
- 监管通报要求核查时，是否能快速定位受影响系统、数据和责任人？

### 建立数据安全事件应急与报告能力

**法规要求｜第43、44条等。** 数据处理者应建立数据安全事件应急机制并按要求处置、报告和演练。

**落实与验收。**

- 建立事件发现、分级、止损、取证、影响评估、报告、通知、恢复和复盘流程。
- 将数据安全事件与网络安全、个人信息保护、人民银行4号令及其他行业事件报告义务做并行映射。
- 预案中明确决策人、监管联系人、备用渠道和关键系统取数方法。
- 按法规频次组织演练，并根据真实事件和演练问题持续修订预案。

**验收标准。**

- 从一次真实异常访问或泄露线索穿行，何时被发现、谁升级、何时止损、何时判断报告？
- 给出“影响范围暂时不清楚但疑似重要数据泄露”的场景，是否会因为等待结论而延迟处置？
- 主负责人和报告渠道不可用时，备用链路是否真的能启动？
- 事件结束后，整改是否进入长期治理而不是只关闭事件单？
