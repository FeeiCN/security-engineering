这篇收录分析样本与图例点评，供选材、组织证据或绘图时按需查阅。工作规则见[安全事件分析原则](/security-incident-analysis-principles)，样本中的写法与结论保留各自的适用边界。

## 可借鉴的分析样本

以下按机制分组，年份标示事件或材料版本，供研究时按需查阅。评价针对各篇能直接核对的写法，不代表其全部结论均已独立验证；不复制整篇结构，也不把历史报告的数据快照、检测指标和应急版本当作当前结论。

### 工控与漏洞研究

| 分析样本 | 好在哪里 | 借鉴时保留的边界 |
| --- | --- | --- |
| [Symantec：W32.Stuxnet Dossier（2010—2011）](https://docs.broadcom.com/doc/security-response-w32-stuxnet-dossier-11-en) | 先解释 PLC 与工程软件的关系，再把目标设备识别、代码替换、运行状态和工业控制行为连起来；另将可能的入侵场景明确标为推测。 | 可借鉴系统背景与代码分析的衔接；承包商、初始投放和准备过程的假设不能改写成已证实经过。 |
| [ESET：Industroyer2（2022）](https://www.welivesecurity.com/2022/04/12/industroyer2-industroyer-reloaded/) | 将电力控制协议、设备配置、定时执行与破坏性组件分别说明，同时直说最初入侵和从 IT 到工控网络的移动方式未知。 | 样本功能、攻击计划和现场实际结果分别举证；不能从具备控制设备的代码推定已经造成停电。 |
| [Securelist：Operation Triangulation（2023）](https://securelist.com/operation-triangulation-the-last-hardware-mystery/111669/) | 先给攻击链概览，再沿寄存器定位、设备树和实验现象展开研究，区分验证到的硬件行为与对用途、发现方式的猜测。 | 专业寄存器与代码细节按读者需要展开，未知设计目的不能改写为蓄意后门。 |

### 勒索、破坏与可用性

| 分析样本 | 好在哪里 | 借鉴时保留的边界 |
| --- | --- | --- |
| [NAO：WannaCry 与 NHS 调查（2017）](https://www.nao.org.uk/reports/investigation-wannacry-cyber-attack-and-the-nhs/) | 区分感染锁机、主动隔离和共享服务引起的中断，继续解释检查结果传递、预约与诊疗受到的影响；交代统计缺失和估算范围。 | 受影响机构不能全部算作被感染，预防性停机的后果也不能全部归为恶意程序直接破坏；统计限于报告覆盖的地区与时间。 |
| [Securelist：NotPetya 的破坏性分析（2017）](https://securelist.com/expetrpetyanotpetya-is-a-wiper-not-ransomware/78902/) | 比较旧变种与本次样本的安装标识、随机数及密钥恢复关系，从代码行为解释为何勒索界面不足以证明可以解密恢复。 | 结论针对所分析的流程；破坏性行为支持对目的的判断，但不能单凭样本证明幕后身份或全部战略意图。 |
| [GitHub：February 28th DDoS Incident Report（2018）](https://github.blog/news-insights/company-news/ddos-incident-report/) | 用流量放大机制解释入口，再把监控异常、值班响应、流量切换与恢复时间对应起来，以吞吐和错误率说明措施效果。 | 攻击流量峰值、用户不可用时间和恢复指标各有含义；这套网络清洗方式有基础设施前提，不能直接推广到所有拒绝服务事件。 |

### 数据泄漏与内部人员

| 分析样本 | 好在哪里 | 借鉴时保留的边界 |
| --- | --- | --- |
| [GAO：Equifax 事件调查（2018 年报告）](https://www.gao.gov/products/gao-18-559) | 把未修补的应用入口、证书过期造成的检测失效、数据库访问范围和数据治理串起来，说明一次漏洞利用为何扩大为持续的数据窃取。 | 攻击过程主要依据 Equifax 及其顾问提供的材料；审计机构发布不等于每个技术环节都经过公开独立复现。 |
| [加拿大隐私专员办公室：Desjardins 调查（2020 年报告）](https://www.priv.gc.ca/en/opc-actions-and-decisions/investigations/investigations-into-businesses/2020/pipeda-2020-005/) | 从受限数据仓库追踪到部门共享目录和 USB 副本，解释正常工作中的复制如何绕过原访问边界，再联系制度执行、监控和保留期限。 | 不能只归因为某个员工恶意或没有制度；法律判断有其辖区与调查范围，不直接变成其他组织的通用合规结论。 |
| [Mandiant：Snowflake 客户实例数据失窃（2024）](https://cloud.google.com/blog/topics/threat-intelligence/unc5537-snowflake-data-theft-extortion) | 将侦察、建立临时 stage、导出和下载数据的动作与脱敏日志、命令对应，让机制解释同时提供可调查的行为线索。 | 正常命令和客户端名称不能单独判定入侵；客户实例调查结论不直接扩大到平台环境或全部客户。 |

### 社工、身份与软件供应链

| 分析样本 | 好在哪里 | 借鉴时保留的边界 |
| --- | --- | --- |
| [NYDFS：Twitter Investigation Report（2020）](https://www.dfs.ny.gov/reports-and-publications/other-reports/Twitter_Report) | 把冒充内部支持的电话、伪造 VPN 登录、MFA 确认与内部工具权限连起来，解释社工怎样转变为操作用户账号的能力。 | 用户账号自身的防护与平台后台权限是不同边界；更广泛的选举和市场风险分析不能写成本次已经发生的后果。 |
| [FireEye / Mandiant：SUNBURST（2020）](https://cloud.google.com/blog/topics/threat-intelligence/evasive-attacker-leverages-solarwinds-supply-chain-compromises-with-sunburst-backdoor) | 从带数字签名的更新包进入机制，解释休眠、合法流量伪装与后续载荷，并把行为分析连接到检测线索及保全证据的处置建议。 | 安装后门、激活及后续入侵分别核对；更新软件可能覆盖证据或留下其他后门，历史修复版本与 IOC 也不能直接作为当前安全证明。 |
| [CircleCI：会话与生产凭证失窃复盘（2022—2023）](https://circleci.com/blog/jan-4-2023-incident-report/) | 从已通过双因素验证的会话被窃讲到生产权限，再解释运行进程中的密钥为何使静态加密不足以隔离本次风险；按时间列出各类撤销措施。 | 不能概括为 MFA 或加密无效；其保护对象与攻击者已取得的能力不同，内部时间线仍依赖厂商调查。 |
| [Cloudflare：Thanksgiving Security Incident（2023）](https://blog.cloudflare.com/thanksgiving-2023-security-incident/) | 说明遗漏轮换的服务凭证为何仍然有效，并区分仓库被访问、被归档下载到内部服务器、是否已向外传出，以及为何按泄漏风险处置。 | 风险处置假设不等于已经证明外传；公开正文没有附完整内部取证记录，其归因与影响范围仍是当事方披露。 |
| [Mandiant：3CX 供应链攻击（2023）](https://cloud.google.com/blog/topics/threat-intelligence/3cx-software-supply-chain-compromise) | 用样本代码与配置的具体相似性支撑关联，在构建环境分析中明确修正此前的恶意软件分类，读者能追踪判断如何改变。 | 样本相似、两次入侵存在联系与攻击者归属分别论证；共用公开工具不能单独证明同一组织。 |
| [Andres Freund：XZ 后门初始披露（2024）](https://www.openwall.com/lists/oss-security/2024/03/29/4) | 从 SSH 性能异常与工具报错出发，对比发布包和仓库内容，给出环境条件、快慢对照和调用追踪，并直说尚未弄清的认证细节。 | 借鉴发现问题的推理路径；初始披露有版本和环境限制，不能把其中的未验证推测当作最终攻击机制。 |
| [LiteLLM：v1.107.0 发布链复盘（2026）](https://docs.litellm.ai/blog/security-incident-oct-21-2026-attack-chain) | 按凭证的取得方式与实际用途还原过程，用审计关联解释分支保护为何先拒绝、随后被高权限绕过，并明确纠正初报中的假设。 | 内部审计关联依赖厂商披露；关于攻击者为何使用多份令牌的动机判断，仍须保留推断语气。 |

### 钱包交易与资金追踪

| 分析样本 | 好在哪里 | 借鉴时保留的边界 |
| --- | --- | --- |
| [CertiK：Bybit 技术分析（2025）](https://www.certik.com/blog/bybit-incident-technical-analysis) | 将攻击交易、调用参数、存储槽修改与钱包实现替换连起来，说明一个看似转账的调用为何获得资产控制权。 | 链上控制权变化与链下界面、终端怎样被入侵是不同证据层，后者需结合后续调查。 |
| [Bitquery：币安链上调查（2026）](https://bitquery.io/investigations/binance-hack) | 先解释交易所钱包如何工作，再按链追踪流出和冻结；说明地址选择、价格口径、余额截点及追踪范围，读者能检查数字如何得到。 | 链上记录支持资金流与授权行为，内部入侵路径仍需对照事发方调查；不要照搬不断变化的资产余额。 |
| [CSH / Iknaio：币安攻击分步分析（2026）](https://csh.ac.at/news/the-binance-hot-wallet-hack-step-by-step/) | 把普通签名转账与以太坊委托分开，用授权列表与 nonce 匹配解释委托如何生效，再按资金变化展开，技术细节都有对应作用。 | 重点是链上机制与资金快照，对最初终端入侵的描述依赖币安陈述，不能据此补全内部网络。 |
| [Cointegrity：币安事件初步分析（2026）](https://cointegrity.substack.com/p/the-binance-hack-of-29-october-2026) | 开头声明证据截点和判断等级，另列来源冲突与尚未完成的独立核验，让读者看见研究仍缺什么。 | 借鉴透明度；“已确认”等标签仍需检查来源独立性与证据含义，不能照搬早期归因和损失结论。 |

## 本站币安稿的取舍

[币安热钱包事件分析](/binance-hot-wallet-incident)值得保留的做法，是先解释有效签名怎样执行了未经授权的操作，再展开终端、部署凭证、签名服务和链上委托之间的关系。稿件没有把终端防护未检出写成零日漏洞，没有把内部 AI 工具的参与补写成某种具体利用方式，也区分了冻结、补足和追回。

旧稿曾在处置段说明措施可按依赖并行处理，却又用文本箭头表示串行；概括性的防线、验证和结语也反复出现相近判断。修订将处置连线指向实际改变的对象，合并重复解释，并单独用状态图说明链上委托的持续与清除。审校仍需注意：对签名服务未确认真实业务意图的解释，应保持为基于已知路径的分析，不能当作已经披露的内部实现。撤销要求按已签署、已广播和已生效等状态确定验收条件，避免承诺可以阻止已经发生的不可逆结果。

以下依据实际查看的原图及所在段落评价表达方式；图中的事件判断和金额仍按原文的证据与时间范围理解。

| 图例与位置 | 值得借鉴的表达 | 重画时需要注意 |
| --- | --- | --- |
| [Stuxnet 报告第 36 页图 19、第 42 页图 26](https://docs.broadcom.com/doc/security-response-w32-stuxnet-dossier-11-en) | 先用控制电脑与 PLC 的读写关系建立背景，再用状态图表达等待、触发、执行和重置，区分系统结构与程序行为。 | 状态只有数字时仍需反复查正文，节点应补状态名；按实际页码和图题核对，不能只凭正文交叉引用找图。 |
| [Industroyer2 图 1](https://www.welivesecurity.com/2022/04/12/industroyer2-industroyer-reloaded/) | 部署关系向不同恶意组件分支，再按工控与 Linux、Solaris 环境分组，避免把多路部署误画成一个串行过程。 | 这是组件与目标环境概览，没有证明最初入口或跨网移动方式；重画时不能补成完整入侵路径。 |
| [3CX 图 1 与图 2](https://cloud.google.com/blog/topics/threat-intelligence/3cx-software-supply-chain-compromise) | 图 1 展示供应链受害者继续成为下游传播源；图 2 将样本、组织与域名、IP 的关联另行展开。 | 为关联线补“使用”“解析到”等含义，不将关联图读成时间线；需要解释中间权限变化时补局部图或注明未知。 |
| [Snowflake 的 Attack Path Diagram 与 Campaign Timeline](https://cloud.google.com/blog/topics/threat-intelligence/unc5537-snowflake-data-theft-extortion) | 将设备窃密、取得凭证、客户实例登录与外传串联；调查和通知的日期另放时间线，使路径与时序各有侧重。 | 等距日期不等于等时长；窃密来源与后续使用凭证的主体也要分清，不能凭一条连续线推定同一攻击者完成所有步骤。 |
| [SUNBURST 图 2：Post-compromise tactics](https://cloud.google.com/blog/topics/threat-intelligence/evasive-attacker-leverages-solarwinds-supply-chain-compromises-with-sunburst-backdoor) | 星形布局适合概览攻击者使用的多种战术。 | 它没有给出战术的先后或因果；需要解释攻击过程时，应另画路径，不把各分支强行串接。 |
| [NHS 调查图 1：影响范围](https://www.nao.org.uk/reports/investigation-wannacry-cyber-attack-and-the-nhs/) | 按医疗机构类型分组，并把已知与未知影响分区，感染、业务受阻和诊疗活动有各自的标签。 | 分类、统计对象与估算不能混加；未知区不等于无影响。原图为横向印刷排版，网页上应调整阅读方向和文字密度。 |
| [GitHub DDoS 复盘中的流入、流出与边缘流量图](https://github.blog/news-insights/company-news/ddos-incident-report/) | 用可观察流量展示异常、转移和后续变化，使响应叙述有指标可对照。 | 原仪表盘各图的时间标示和纵轴范围需要核对，重画时统一或注明；峰值、用户不可用与恢复分别解释。 |
| [Cointegrity 的事件时间图与攻击路径图](https://cointegrity.substack.com/p/the-binance-hack-of-29-october-2026) | 时间图按攻击者、外部响应者和平台分行，突出委托持续区间；路径图分别标明平台陈述和根据签名作出的推断。 | 借鉴证据分层与跨方对照，不照搬初步资料中的精确时刻；密集金额与地址可移到细节表。 |
| [Bitquery 的转出分支、USDT 冻结窗口与资金去向图](https://bitquery.io/investigations/binance-hack) | 将普通转账与持续委托分开；把资产停留区间与冻结时点放在共同时间轴，直接显示冻结是否赶上；资金去向图说明不同估值截点。 | 转移量、余额与冻结状态分别处理，不能为凑齐总额混用估值。宽图可保留图内滚动，但仍需检查左右端及关键注释能否完整读到。 |
| [CertiK 的 Bybit 交易截图](https://www.certik.com/blog/bybit-incident-technical-analysis)、[NotPetya 的随机数据与安装标识截图](https://securelist.com/expetrpetyanotpetya-is-a-wiper-not-ransomware/78902/) | 前者圈出 `operation` 字段，后者对照数据生成与结果，用局部证据支撑具体技术判断。 | 保留字段含义、代码上下文和原记录入口；避免用截图中密集的字节、弹窗或完整界面代替机制解释。 |
| [Operation Triangulation 的 Attack chain 图](https://securelist.com/operation-triangulation-the-last-hardware-mystery/111669/) | 将多阶段利用沿主线排列，把清理操作作为支线，阶段旁保留相关漏洞与作用。 | 长链和术语密集时先给阶段概览，再局部展开；不能让每个漏洞编号都与关键边界争夺注意力。 |
